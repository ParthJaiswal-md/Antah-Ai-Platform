 1. ONE-PARAGRAPH OVERVIEW
================================================================================
 A 3-system platform for India's Official Statistical System. A government
 official's skills are compared against what their job role demands; skill
 gaps are computed; training courses from a 784-course catalogue are ranked to
 close those gaps (System 1). Each recommended course can be turned into a
 quick comprehension quiz that is auto-generated from a real lecture video
 (System 2: download -> transcribe -> LLM writes MCQs -> fact-check). System 3
 is the friendly full-stack web app "Antah.ai" that a trainer/official logs
 into: it collects the intake form, calls System 1 for recommendations, shows
 the top-5 courses, lets the user "Take a quiz" per course (running System 2 in
 the background), grades it, and keeps a per-employee profile of who quizzed
 which course and how well — with a "Take a quiz" button left on any course
 that has not been attempted yet.

 Systems 1 and 2 are separate codebases owned by different teammates; System 3
 is the integrator that calls System 1 over HTTP and imports System 2's
 functions in-process. None of the three is duplicated inside another.

================================================================================
 3. END-TO-END USER WORKFLOW (the "story")
================================================================================
 Trainer/official opens http://127.0.0.1:8080  (System 3, served by Flask).

  1. LANDING -> REGISTER / LOGIN
       Username + password. Passwords are PBKDF2-SHA256 hashes (120k iterations,
       salt derived from the username, stored as salt$digest) in antahai.db.

  2. RECOMMENDATION INTAKE (page "/recommendation")
       Form built from live System 1 metadata:
         - Pick a DESIGNATION -> only valid DEPARTMENTS appear (cascading),
           the ROLE_ID is the designation+department pair from System 1.
         - Rate 16 skills 1-3 (Beginner/Intermediate/Advanced), optionally list
           previous trainings (course picker), work experience, education, etc.
       Submit -> S3 POSTs a NewEmployeeInput to System 1's /employees/register.

  3. SYSTEM 1 COMPUTES
       - gap = required_role_level - current_level (only >0 are gaps)
       - ranks courses; returns top-5 + the profile (assigns next E### id)
       - writes the new employee INTO Dataset-5 (real store) + stores the
         recommended course_ids in a recommended_courses column
       S3 saves its own snapshot row (submissions table) for history.

  4. RESULTS PAGE (per employee)
       "Thank You / Employee ID / lead line / one-line summary -> the 5 course
       cards." Each card shows provider/mode/duration/language/skills covered,
       and a quiz action button (Take a quiz / Continue quiz / View score).

  5. "TAKE A QUIZ" (per recommended course)
       S3 picks a RANDOM lecture video from Dataset-6 (20 YouTube links) and
       fires a background thread that runs System 2's pipeline on it:
          yt-dlp download -> ffmpeg audio -> Whisper transcript -> Groq MCQs
          -> structural validation -> LLM fact-check
       User sees a spinner page that polls status; when ready, the quiz renders
       (radio buttons). Submit -> S3 grades (case-insensitive exact match),
       shows score + per-question review with verification badges.

  6. PROFILE (history, "/profile")
       Lists every employee the user registered. Under each employee, each
       recommended course shows exactly one action:
         - score link  if the quiz was taken & graded (e.g. "Quiz: 3/5 (60%)")
         - Continue quiz if a quiz exists but wasn't finished
         - "Take a quiz" button if the course has NOT been attempted (new)
       A back (<-) arrow sits top-right beside the avatar ON THE PROFILE ONLY;
       it returns to whichever page the user came from (browser-back with a
       safe fallback).

  The same journey is testable end-to-end without any network/LLM by setting
  ANTAHAI_FAKE_QUIZ=1 (serves a canned 3-question quiz) and without touching
  the real Dataset-5 by pointing S1 at a temp copy (S1_DATA_DIR).

 5. SYSTEM 1 — RECOMMENDATION ENGINE (deep dive)
================================================================================
 5.1 Identity
   Problem : "Given an official's current skills and their role's required
             skills, which courses close the gaps?" Pure data service. NO quiz
             generation, NO auth, NO enrollment tracking, NO live iGOT API
             (Dataset-4 is the mock course catalogue).

 5.2 Code layout (strict layering: routes -> services -> repositories -> CSVs)
   app/main.py                   app assembly: load CSVs, build repos/services,
                                 CORS, routers, serve web UI at "/" + /health
   app/config.py                 paths + tunables (env-overridable via S1_*)
   app/data/loader.py            Stage A: read/clean/parse CSVs, thread-safe writes
   app/data/repositories.py      Skill/Role/Employee/Course lookup objects
   app/services/gap_service.py   Stage B: skill-gap calculation
   app/services/recommendation_service.py  Stage C+D: ranking + unmatched gaps
   app/services/registration_service.py    persist new employee + compute
   app/services/analytics_service.py       admin aggregations over workforce
   app/models/schemas.py         Pydantic models = the stable JSON contract
   app/api/routes.py             thin HTTP layer
   frontend/index.html           single-page intake UI (served at "/")
   tools/interactive_intake.py   CLI intake wizard (terminal twin of the UI)
   datasets/                     Dataset-1..4 + Dataset-5 (grows at runtime)
   context/                      team docs + build spec + requirements
   tests/                        pytest suite (50+ tests, all passing)

 5.3 The five datasets (the data truth)
   Dataset-1 Skill taxonomy       16 skills S001-S016; cols: skill_id,
          skill_name, category (Technical | Statistical | Digital Governance |
          Behavioural-Managerial), description, proficiency_levels ("1,2,3").
   Dataset-2 Required competency  800 rows, ~60 roles R001-R060; cols: role_id,
          designation, department, skill_id, required_level(1-3),
          priority_weight(1-3). ~12-15 required skills per role.
   Dataset-3 Synthetic employees  805 profiles E001-E805; cols: employee_id,
          name, role_id, designation, department, current_assignment,
          educational_qualifications, work_experience_years, previous_trainings,
          self_rated_skills, quiz_verified_skills.
   Dataset-4 Course catalogue     784 courses C001-C784; cols: course_id,
          course_title, description, skill_tags, target_level(1-3),
          duration_minutes, mode (self-paced|instructor-led|virtual-lab),
          provider, language (English|Hindi|English/Hindi).
   Dataset-5 Real employees       same cols as D3 + registered_at +
          recommended_courses (the 13th column, comma-packed course_ids that
          were recommended for THAT registration, written by register()). Starts
          effectively empty and GROWS with every real registration; the engine
          auto-assigns the next free E###. As of 2026-09-09 it holds 6 rows
          E806-E811: E806 Parth Raj Jaiswal, E807 Anuj Agarwal, then a few
          Exx1-Exx3 demo/test registrations. A .bak of the
          pre-migration header sits next to it. NEVER treat it as static.

   PACKED-STRING FORMATS (parsed once at load, never in business logic):
     self_rated_skills / quiz_verified_skills :  "S001:2;S002:1;..."  (skill:level)
     previous_trainings                       :  "C649,C067,..."       (course ids)
     skill_tags                               :  "S013,S010,..."       (skill ids)
   Quiz-verified values OVERRIDE self-ratings during gap computation (the
   verified signal is more trustworthy). Missing skill => level 0.

   KNOWN DATA GAP (intentional, not a bug): no course is tagged S014 (Cloud
   Computing) -> S014 gaps trigger the explicit "no courses available" report
   (5.6 Stage D) rather than a silent empty answer.

 5.4 Config (app/config.py, env-prefixed S1_)
   S1_DATA_DIR     default <repo>/datasets   where the CSVs live
   S1_CORS_ORIGINS default *                  comma-separated CORS origins
   Fixed: DEFAULT_TOP_N=5, MAX_TOP_N=50, MAX_LEVEL=3,
          REAL_EMPLOYEE_COLUMNS (13 entries incl. recommended_courses).

 5.5 Pipeline
   Stage A  Load: read CSVs, strip whitespace (cells AND column names), parse
            packed fields, FK-validate (log-only). Repositories wrap the frames.
   Stage B  Gaps (GapService):
              current_level = quiz_verified if present else self_rated else 0
              gap = required_level - current_level ; keep only gap > 0
              sort: largest gap first; tie-break higher priority_weight then
              skill_id. Output: {skill_id, skill_name, current_level,
              required_level, gap, priority_weight}.
            Already-qualified employee => EMPTY list (valid, not an error).
   Stage C  Course ranking (RecommendationService):
              candidates = courses whose skill_tags contain a gap skill
              matched_weight    = sum(priority_weight) of gap skills covered
              level_relevance   = 1/(1+|course.target_level - max required level
                                  among matched gaps|)   (1.0 when exact)
              raw score         = matched_weight * level_relevance
              scores normalized so best = 1.0; sort desc (tie: course_id);
              truncate to top_n (default 5, max 50).
              Each rec: {course_id, course_title, description, target_level,
              duration_minutes, mode, provider, language, matched_skills[],
              score}. Only genuinely-tagged courses are ever recommended.
   Stage D  Unmatched gap reporting: a gap skill with ZERO courses returns
              {skill_id, skill_name, status: "no_courses_available", message}
              — never silently dropped, never crashes, never faked. (status is
              machine-readable for banners.)
   Stage E  API (below).
   Stage F  Sanity guarantees (tested): already-qualified -> empty; S014 gap ->
              explicit report; typical profile -> plausible tagged courses.

 5.6 HTTP API surface (Swagger auto-docs at /docs)
   GET  /employees/{id}/gaps                  gaps for a stored employee
   GET  /employees/{id}/recommendations?top_n gaps+recs+unmatched for employee
   GET  /employees/{id}/profile               raw profile (parsed)
   POST /employees/compute?top_n              same pipeline, STATELESS (preview)
   POST /employees/register?top_n             persists to Dataset-5 (201), hot-adds
   POST /employees/{id}/skills                update skill levels (S2 writeback)
   GET  /employees/recommendations/batch?top_n  gaps+recs for ALL employees
   GET  /analytics/synthetic | /real | /combined | /registrations
   GET  /meta/skills | /roles | /courses | /unique-values   (form builders)
   GET  /health    -> {status, employees_loaded, synthetic 805, real n, courses 784}
   GET  /          -> the web intake UI (same origin, no CORS needed)

   KEY CONTRACT DETAILS (System 3 depends on these — do not break):
   - Response key names EXACTLY match CSV column names (skill_id, course_title).
   - POST /employees/register body = NewEmployeeInput:
       {name, role_id(R001-R060), designation, department, current_assignment,
        educational_qualifications, work_experience_years,
        previous_trainings[course_ids], self_rated_skills{skill_id:level},
        quiz_verified_skills{}  <-- MUST be {} for fresh S3 registrations}
     Response (ComputeResponse): {employee{...}, gaps[], recommendations[],
        unmatched_gaps[]}. Recommendation field is course_title (NOT "title").
   - register without employee_id -> auto next E###; duplicate id -> 409.
   - Errors: 404 unknown id; 422 invalid top_n/role/skill/level(1-3)/
     experience(0-80)/empty skill update; 409 duplicate registration.
   - Skill update example:  POST /employees/{id}/skills
       body {"quiz_verified_skills": {"S002": 3}}  -> merges + persists to the
     right CSV (D3 synthetic / D5 real) so the very next gap call reflects it.
     This is the OFFICIAL System-2 quiz write-back path (see 8.4 for S3 status).
   - CORS enabled from day one (no auth here).

 5.7 Frontend & recent changes
   S1 ships a single-page intake UI (frontend/index.html) at http://localhost:8000/
   and a CLI twin (tools/interactive_intake.py).
   RECENT (2026-09) frontend work:

 5.8 Tests & design decisions
   50+ pytest cases across test_sanity/gap_service/recommendation_service/
   compute_endpoint/dataset5/integration_additions. Run: python -m pytest -v
   Key decisions: strict layering; schema-validated JSON contract; ONE shared

   answers); quiz-verified > self-rated; explicit unmatched-gap status; real vs

 6. SYSTEM 2 — MCQ GENERATOR (deep dive)
================================================================================
 6.1 Identity & stack
   Purpose : turn a lecture (video file / direct URL / YouTube link / even a
             PDF) into fact-checked multiple-choice questions.
   IMPORTANT SCOPE FACT: S2 reads NO dataset/CSV anywhere (no pandas/csv import
             in the whole tree). Lecture links come only from user input at
             request time (file upload or pasted URL). In the integrated
             product System 3 supplies the link from ITS Dataset-6 — the
             dependency is one-way: S3 -> S2.
   Stack   : Python 3.13 venv (.venv) · Flask 3.1 · yt-dlp · ffmpeg ·
             openai-whisper · langchain-groq 0.3 ChatGroq · PyPDF2 · python-dotenv ·
             SQLite. Frontend = plain CSS + Jinja2 (port 5050 in standalone use).
             (transformers / langchain-community are declared deps but never
             imported — dead weight.)

 6.2 Module map
   app.py                        Flask routes (course setup, lecture/final quiz,
                                 results), its own _download_video/_run_pipeline
   utils/video_processor.py      audio extraction from video via bare `ffmpeg`
   utils/audio_transcriber.py    Whisper transcription
   utils/mcq_generator.py        MCQ generation + validation + LLM fact-check
   utils/question_manager.py     question-bank slicing per lecture / final quiz
   utils/results_manager.py      SQLite quiz-attempt storage + progress summaries
   prompts/mcq_prompt.txt        the LLM system prompt for writing MCQs
   question_bank/questions.json  fallback/static bank
   templates/ (index/quiz/result.html), static/, uploads/, results.db, .env

 6.3 The pipeline (in exact order — as invoked by System 3, but identical to S2's own)
   STEP 1  VIDEO ACQUISITION
       S3 (or S2 app) downloads the link. S3 uses its own s2_bridge.download_video
       = yt-dlp with format "bv*+ba/b", merge to mp4, noplaylist, and
       extractor_args youtube player_client = ["android"] (settings.YT_CLIENTS).
       WHY android: YouTube blocks anonymous web-client downloads with
       "Sign in to confirm you're not a bot"; the android player client currently
       bypasses it (verified). Do NOT revert to the default web client.
       NOTE: System 2's OWN standalone _download_video does NOT set
       player_client — its default (web) client is the fragile YouTube path.
       Only S3's bridge carries the android workaround.
   STEP 2  AUDIO EXTRACTION  (utils/video_processor.process_video -> audio file)
       ffmpeg -y -i <video> -q:a 0 -map a <audio>   (bare `ffmpeg` -> needs the
       ffmpeg bin dir on PATH; S3 prepends it).
   STEP 3  TRANSCRIPTION  (utils/audio_transcriber.transcribe_audio)
       whisper.load_model(model). Model = env WHISPER_MODEL or "tiny" (tiny =
       fast, for demo/speed). Larger base/small/medium/large = slower, better.
   STEP 4  MCQ GENERATION  (utils/mcq_generator.generate_mcqs)
       LLM = ChatGroq(model_name="openai/gpt-oss-20b", temperature=0.3,
       max_tokens=8192) via LangChain prompt|llm|StrOutputParser, invoked with
       {context: transcript, num_questions, topic}.
       Note: max_tokens was raised to 8192 so long JSON outputs don't truncate.
   STEP 5  STRUCTURAL VALIDATION  (validate_mcqs(questions, transcript))
       keeps a question only if: its answer is literally one of its options;
       it is not a duplicate; and (if it has a source_snippet) the snippet
       resembles the transcript (difflib SequenceMatcher ratio >= 0.6, else it
       sets grounding_warning=True instead of dropping).
   STEP 6  LLM FACT-CHECK  (verify_mcqs(questions, transcript))
       second ChatGroq pass (temperature 0, max_tokens 4096) re-reads each
       question against the transcript and replies ONLY with the ids of
       questions it judges INACCURATE or NOT SUPPORTED. Those ids become
       flagged; the rest verified; a question whose source_snippet failed
       grounding (STEP 5) is force-flagged. Flagged questions are KEPT, never
       dropped — so the "Flagged" count in the UI is meaningful. If the LLM
       reply can't be parsed (or the call itself fails), the WHOLE batch
       silently downgrades to unverified rather than erroring out.

   Question object fields (S2): question text, options[] (4), answer,
   explanation, source_snippet (the grounding sentence), topic/concept,
   difficulty (Easy/Medium/Hard), + after verification verification_status.
   S3 renumbers ids 1..N and coerces options to a list on ingestion.

 6.4 S2's OWN standalone app (not used in the integrated flow)
   Course setup collects total lectures + questions-per-lecture; per-lecture
   quizzes slice the generated bank; a final quiz uses leftover questions;
   /result shows attempt totals, correct/incorrect, accuracy and a full
   question-by-question review. Every attempt persists to results.db keyed to
   an anonymous per-session user id -> improvement summaries. Standalone:
   python app.py -> http://localhost:5050  (5050 chosen to avoid macOS AirPlay
   squabbling over 5000). Requirements in requirements.txt.

 6.5 Env vars & secrets
   .env holds GROQ_API_KEY (required; read at IMPORT time of utils.mcq_generator
   via its own load_dotenv + os.getenv -> importers must export it BEFORE
   importing the module) and WHISPER_MODEL (optional, default tiny; the default
   "tiny" fallback is why tiny is the effective model even though the
   AudioTranscriber class header says "base"). NEVER print/commit the key.

 6.6 Quirks that bite
   - prompts/mcq_prompt.txt is opened relative to the CURRENT WORKING DIRECTORY
     on each call -> callers must os.chdir into the S2 root around the pipeline.
   - Bare `ffmpeg` subprocess -> ffmpeg must be reachable (PATH or prepend).
   - S2 imports are heavy (torch/whisper load lazily inside the call).
   - S3 embeds ALL of S2's utils via in-process import; S2 never runs as a
     server in the integrated product (S2's own app.py/5050 is the standalone demo).
   - GROQ_API_KEY is read once at import -> editing .env needs a process restart.

 6.7 S2 standalone-app caveats (for the S2 owner / an honest PPT slide)
   The standalone S2 demo works but has single-user / demo-grade assumptions —
   fine for the demo, NOT production-shaped. Teammates extending S2 should know:
   - The generated question bank is a PROCESS GLOBAL (module-level ALL_QUESTIONS)
     rebound on every course start and read by /result -> two browsers on the
     same process overwrite each other's questions. Multi-user unsafe by design.
   - The whole transcript is stored in the Flask COOKIE session (~4 KB limit) ->
     long lectures silently break the standalone app.
   - app.secret_key is hardcoded ("sih-secret-key") and debug=True — demo only.
   - Grading = full-string case-insensitive compare of option text (no trim/
     punctuation normalisation) in TWO spots with slightly different totals: the
     /result page skips unanswered questions for its denominator, while
     results.db counts the whole shown batch (an unanswered one scores wrong
     there) -> two accuracy figures can differ.
   - NO test suite exists anywhere in S2 (verified).
   - Dead/orphan files ship in the tree: utils/summarizer.py + pdf_reader.py
     (PDFQuizzer leftover; never imported), empty duration_manager.py,
     orphaned static/css/style.css + static/js/script.js (bind to element ids
     that no template has), and question_bank/questions.json is only the
     pre-generation fallback. Its shape differs from generated questions
     (options dict with letter answers vs a list with text answers) — before
     any course is generated the static bank renders "a/b/c/d" as the choices.
   - S2's yt-dlp call lacks the player_client android workaround (see STEP 1);
     standalone YouTube downloads are the fragile path.
   None of these affect the S3-integrated flow (S3 does not run S2's app.py).

 7. SYSTEM 3 — "Antah.ai" WEB SHELL (deep dive)

 7.1 Identity
   Full-stack glue that presents S1 + S2 as one product. Owns accounts and
   history only. It does NOT reimplement recommendation or MCQ logic.
   Folder on disk: System-3 Complete_Website (historically Complete_Linker).
   Design notes captured in SYSTEM3_FULLSTACK_BUILD_SPEC.md (same folder).

 7.2 Code layout
   app.py            Flask routes / auth / sessions / page flow / quiz job thread
   db.py             sqlite3 persistence (users, submissions, quiz_attempts),
                     grading + review helpers
   settings.py       all paths/ports/constants (env-overridable ANTAHAI_*)
   s1_client.py      stdlib-urllib HTTP client for System 1 (5-min meta cache)
   s2_bridge.py      in-process bridge into System-2 utils (yt-dlp + pipeline)
   run_antahai.py    launcher: boots S1 (:8000) then S3 (:8080); Ctrl+C stops both
   Dataset-6 Youtube_Links.csv   20 YouTube links (S.No,Link) used as quiz source

 7.3 Database schema (antahai.db)
   users          id, username(unique), password_hash(PBKDF2-SHA256 salt$digest),
                  created_at
   submissions    one row per intake form submission: user_id, employee_id,
                  name, role_id, designation, department, current_assignment,
                  educational_qualifications, work_experience_years,
                  previous_trainings(JSON), self_rated_skills(JSON),
                  quiz_verified_skills(JSON), recommendations(JSON snapshot —
                  the exact courses S1 returned, enriched with matched_skill_names),
                  submitted_at
   quiz_attempts  id, user_id, submission_id, course_id, course_title,
                  source_link(Dataset-6 url), status, error, quiz(JSON Q-bank),
                  answers(JSON), score, total, accuracy, created_at, finished_at
   Ownership enforced in app: attempts/submissions 404 if not the session user's.
   Retake rule is a UI notice ONLY (settings.ONE_ATTEMPT_NOTICE) — no backend
   enforcement.

 7.4 Quiz attempt lifecycle (statuses)
   generating  ->  ready   ->  graded      (or ->  error)
   generating : background S2 pipeline running (page polls /quiz/<id>/status.json)
   ready      : questions stored; user may answer
   error      : pipeline failed (message stored); the UI lets you retry
   graded     : answered + scored (score/total/accuracy + answers + review kept)
   "Take a quiz" on a course REUSES an existing generating/ready attempt
   (redirects to it) instead of spawning a duplicate; an error attempt is not
   reused, so clicking again starts a fresh one (= free retry).

 7.5 Grading convention
   case-insensitive full-string match of the selected option vs the stored
   answer; score = number correct; accuracy = score/total %. Same scorer used
   for grading and for re-rendering a graded attempt's review.

 7.6 Routes (S3)
   GET  /                     landing (redirects to /recommendation if logged in)
   POST /api/register         create user (JSON)
   GET|POST /login            login (JSON; 401 on bad password)
   GET  /logout
   GET|POST /recommendation   intake form (GET) / register employee (POST JSON,
                              relays to S1, creates submission, 302-> results)
   GET  /recommendation/results/<submission_id>
   POST /quiz/start           starts quiz for {submission_id, course_id}
   GET|POST /quiz/<attempt_id>       status page or quiz-taking / submit+grade
   GET  /quiz/<attempt_id>/status.json   polled by the spinner page
   GET  /quiz/<attempt_id>/results      score + per-question review
   GET  /profile               employee history (see 3.6)
   All post-login pages extend templates/base.html (shared nav: Antah.ai brand
   left, avatar dropdown right = Profile / Logout). PROFILE ONLY adds the
   back-arrow (it is opt-in per-page via a nav_back block).

 7.7 s2_bridge internals (quiz generation)
   ensure_ready(): idempotently (1) put S2 root on sys.path, (2) load S2/.env
   into os.environ BEFORE importing utils.mcq_generator (key read at import),
   (3) prepend ffmpeg bin to PATH, (4) import S2's utils (whisper/torch load
   lazily later). Import lock.
   generate_quiz(link, topic, num_questions=5):
     os.chdir(S2 root) [prompt file is CWD-relative] -> download_video(yt-dlp,
     android client) -> process_video (ffmpeg audio) -> transcribe_audio
     (whisper tiny) -> generate_mcqs -> _parse_generated_questions (renumber,
     options->list) -> validate_mcqs -> verify_mcqs -> restore cwd -> delete
     temp video+audio. PIPELINE_LOCK serializes jobs (only one at a time).
     QuizPipelineError raises user-facing messages.
   ANTAHAI_FAKE_QUIZ=1: app._run_quiz_job skips the whole S2 pipeline and
   stores a canned 3-question quiz instantly (offline demo/tests).

 7.8 s1_client internals
   Pure stdlib urllib. ping(), meta_skills/roles/courses_light/unique_values
   (300s TTL cache), register_employee(payload, top_n=5). S1Error carries the
   engine's message; S1Unavailable when the engine is down (S3 shows a friendly
   "cannot reach" page instead of crashing).

 7.9 What's genuinely running on which Python (IMPORTANT)
   System 1  -> the DEFAULT `python` (has fastapi/uvicorn/pandas) runs uvicorn :8000
   System 3  -> the SYSTEM-2 VENV python (has flask; S1's deps are NOT there)
               runs app.py :8080  — because S3 imports S2's utils in-process,
               which only exist in the S2 venv.
   run_antahai.py starts both, waits for S1 to answer /health, prints the URLs.

 7.10 Verification story
   smoke_e2e.py        offline: stubs S1 client functions + ANTAHAI_FAKE_QUIZ=1,
                       walks register->login->intake->results->quiz->grade->
                       profile->logout, 24 checks incl. the new profile
                       "Take a quiz" and the profile-only back button.
   integration_live.py real: boots real S1 against a TEMP S1_DATA_DIR copy of
                       the datasets + real S3 (real DB in a temp dir), registers
                       a live employee, asserts the REAL Dataset-5 is byte-
                       identical afterwards (the temp copy got the new row).
   Run both with the System-2 venv python from the S3 folder.

 8. HOW THE SYSTEMS INTEGRATE (contracts & seams)
================================================================================
 8.1 Topology
        System 3 (Flask :8080)
          |--HTTP--> System 1 (FastAPI :8000)     recommendations + metadata
          |--import in-process--> System 2 utils  quiz generation (no server)
        System 2 standalone app (:5050) = the S2 team's own demo, NOT used by S3.
   Launch everything with:  run_antahai.py (S2-venv python) from the S3 folder.

 8.2 System-1 contract S3 relies on (stable — matches CSV column names)
   NewEmployeeInput/ComputeResponse as in 5.6. quiz_verified_skills must be {}.
   register auto-numbers E###. Recommendations carry course_title + matched_skills
   (skill ids); S3 enriches matched_skill_names client-side from /meta/skills so
   pages render without re-calling S1. S3 stores a submissions snapshot so
   history renders offline.

 8.3 System-2 contract S3 relies on
   S3 imports S2's utils.mcq_generator/audio_transcriber/video_processor in its
   own process. Contract = function signatures + the two gotchas (GROQ key must
   be exported before import; CWD must be the S2 root while prompting). S3 also
   reuses S2's download options but pins the android player client.

 8.4 Current seams / known gaps (say these honestly in a PPT)
   1. QUIZ -> VERIFIED-SKILL WRITEBACK NOT WIRED: S1 exposes
      POST /employees/{id}/skills (quiz_verified_skills) as the official path
      to lift an employee's verified level after a quiz. S3 currently keeps quiz
      scores ONLY in its own antahai.db and does NOT push verified levels back to
      S1. (In S3's register payload quiz_verified_skills is always {}.) This is
      the natural next integration step.
   2. RANDOM VIDEO PER COURSE: any course's quiz pulls a RANDOM Dataset-6 link,
      not a link matched to the course topic. Works, but questions may not test
      the course content. Future: map courses -> relevant videos.
   3. ONE ATTEMPT PER COURSE is a UI notice only; nothing enforces it server-side.
   4. SYSTEM-2 VENV PYTHON runs BOTH S2 logic and S3's Flask; S1 needs the other
      (default) python. Mind which interpreter you launch.
   5. S1's auth/state scope excludes accounts & enrollment — all user/account
      state lives in S3's antahai.db.
   6. YouTube bot-wall workaround (android player client) is an arms race; if
      it stops working set ANTAHAI_YT_CLIENT or revisit cookies.

 11. SECURITY & DATA-SAFETY NOTES
================================================================================
 - Passwords: PBKDF2-SHA256, 120k iterations, salt deterministically derived
   from the username (stored salt$digest); only in S3's antahai.db. Flask
   sessions are signed cookies.
 - S1 has NO auth by design (internal service); CORS wide open by default —
   lock S1_CORS_ORIGINS before any production exposure.
 - The Groq API key lives ONLY in System-2/.env (git-ignored). Never print it.
 - Dataset-5 is REAL employee data (the store that grows). Tests never touch it:
   integration_live.py runs S1 against a temp S1_DATA_DIR copy and asserts the
   real file is byte-identical afterwards. Mind the 13-column header if you ever
   rewrite Dataset-5 by hand.
 - ffmpeg: expected from the WinGet Gyan build; prepended to PATH by S3.
 - System 3 sessions are Flask-signed cookies; secrets random per boot unless
   ANTAHAI_SECRET is pinned (pin it if you want stable sessions across restarts).
